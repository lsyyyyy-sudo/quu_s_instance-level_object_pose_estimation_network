### 1.2 遮挡分层 —— 这是整个项目的出发点

| `visib_fract` | 角点占比 | 中位误差 | 失败率 >0.1 |
|---|---|---|---|
| 0.0~0.5 | 3.5% | 0.0760 | **45.00%** |
| 0.5~0.8 | 3.7% | 0.0072 | 27.50% |
| 0.8~0.95 | 2.5% | 0.0089 | 0.00% |
| **0.95~1.0** | **90.2%** | 0.0054 | **0.79%** |

**差距 57 倍。** 因果链：被遮挡的角点必须**外推**，而 v1 训练集 95% 实例完全可见
（`DATA-16`），**模型从没学过外推** → 遇到遮挡就瞎猜。

**→ 这是 v2 的设计依据。**

### 1.3 训练曲线结论

前 15 个 epoch 从 30 降到 23，之后 240 个 epoch 只再降到 16.6，
**最后 25 个 epoch 完全没动**。→ **`max_epochs` 设 150~200 就够，500 过量。**

### 1.4 走过的弯路：第一版评测用错了口径

第一次评测打开了 `solve_pose`，报出 `add = 157.84 mm`（物体直径只有 81 mm），
据此得出"6D 位姿完全失败"—— **那是拿错标准打分**。位姿对 70 mm 小物体的 2D
误差极其敏感，会把"角点其实还行"读成"完全失败"。**交付物是 2D 角点，就该用 2D 角点的指标。**

### 1.5 角点提取方式对照（同一 checkpoint）

| 方式 | `corner_err_px` | `pck@0.05` |
|---|---|---|
| `soft_argmax` | **15.82** | **0.8185** |
| `topk(20)`（默认） | 15.99 | 0.8095 |
| `argmax` | 17.29 | 0.8060 |

差距 0.2 px → **问题在数据/模型，不在后处理。**

|---|---|---|
| **v1 模型** | mean **4.12** / PCK@0.05 **96.9%** | mean **72.72** / 32.5% |

### 2.4 逐场景扫描：坏场景是**成片**的

把 39 个分片（52 个场景）逐个评一遍：

```
mean 从 37.80 一直分布到 123.06    （0 个分片 mean < 15）
median 从  7.77 一直分布到 120.99
```

**两个形态：**
- **median ≈ 120**（如 extra1/extra2/extra8）：mean≈median ⇒ **每个角点都错**，均匀失败
- **median ≈ 8~16**（如 extra13/extra17/extra20）：mean 是 median 的 4 倍 ⇒ **重尾**

**关键对照**：

| 分片 | 过滤后 `area(visib)/area(obj) < 0.3` 的比例 | median 误差 |
|---|---|---|
| extra1 | 3.2% | **120.99** |
| extra13 | 2.4% | **8.43** |

**两片的框/可见性统计几乎一样，结果差 14 倍** ⇒ 差异不在框上。

### 2.5 被证伪的假设（六条，全部实测）

| # | 假设 | 检验方式 | 结果 |
|---|---|---|---|
| 1 | 标签错位 | 全图/裁剪/`corner_2d` 三者一致性 | ❌ 完全一致 |
| 2 | 几何不一致 | 投影框/`bbox_visib` 面积比 | ❌ 两边都是 **1.25** |
| 3 | 姿态分布单一 | 物体各轴与光轴夹角分布 | ❌ "有面正对相机" 31.7% vs 26.0% |
| 4 | 亮度偏移 | 全帧灰度分布 | ❌ v2 有 **98.7%** 的帧落在 v1 范围内 |
| 5 | `BP_NUM_WORKER` 路径有 bug | 实例上 4 vs 0 各渲一场景 | ❌ **逐位相同**（mean 6.79 / 6.79） |
| 6 | 裁剪框用错（`bbox_visib` vs `bbox_obj`） | 切换开关对比 | ❌ 122.26 → **120.67**，几乎没变 |
| 7 | topk/soft_argmax 算子脱节 | 两者误差对照 | ❌ v1: 4.11/4.05；v2: 225/224 —— **高度一致** |
| 8 | `bbox_visib` 脏 | 过滤后统计 | ❌ 只有 **2~4%**，不足以造成 median=121 |

### 2.6 ✅ 找到的真问题：**"无解样本"**

`data/results/stage3_train_v1/v2_hard_occlusion.jpg`（5 个样本，按可见度排序）：

| 行 | `visib_fract` | 可见像素 | 模型误差 | **裁剪图里有物体吗** |
|---|---|---|---|---|
| 1 | 1.00 | 32,473 | **2.8 px** | 完整 |
| 2 | 0.50 | 16,247 | 32.9 px | 有，露一半 |
| 3 | 0.36 | 12,310 | 39.1 px | 有，露一部分 |
| **4** | **0.24** | 10,335 | **228.1 px** | **几乎没有** |
| **5** | **0.11** | 4,191 | **241.9 px** | **完全没有，纯空白** |

**第 4、5 行的裁剪图是空白的米色平面 —— 没有任何物体 —— 却要求模型输出 8 个具体坐标。**

**注意第 4 行有 10,335 个可见像素（相当多）照样崩到 228 px。**
问题不是"像素不够"，是**那些像素不在裁剪图里** —— 正是 `bbox_visib` 退化造成的：
真正可见的部分是画面一角的小斑，绿框（`bbox_visib`）套在那里，裁剪自然取不到物体。

**而我们的过滤器把它们全放进来了**：`min_visib_fract=0.10` + `min_px_visib=64`，
第 5 行 `visib=0.11` **刚好在阈值上面**。

**→ 18% 的 v2 实例是这一类。它们贡献的梯度方向是"从空白/箱壁纹理映射到特定坐标"
—— 纯粹在教模型学伪相关。** 这与"从头训也拟合不了"完全一致。

### 2.7 语义层面的设计缺陷

```
裁剪用   bbox_visib  —— "看得见的部分"的框
标签是   3D 盒 8 角点投影 —— amodal，包含被挡住的部分
```

**两者语义不一致。** v1 侥幸没暴露（**95.3% 的实例 `bbox_visib == bbox_obj`**），
v2 加料箱造遮挡后立刻引爆。

已加开关 `datamodule.crop_use_bbox_obj`（默认 `false` 保持 v1 历史行为）。
**但注意实测把它打开对 v2 帮助很小**（122.26 → 120.67）—— 它修的是**语义正确性**，
不是 v2 那个量级的问题。

### 2.8 场景级质检门（`scripts/qa_scene.py`）

渲完一个场景先用参考模型打分（20 秒），不合格就丢。

| 场景 | 归一化 median | 失败率 | 判定 |
|---|---|---|---|
| **v1** | **0.0054** | 1.3% | PASS |
| v2 extra13 | 0.0325 | 31.2% | FAIL |
| v2 extra1 | 0.4478 | 93.4% | FAIL |
| 试渲 ×3（bin, n=10, elev=22） | 0.0219 / 0.0780 / 0.0355 | 27.6 / 45.9 / 38.8% | 3× FAIL |

## 3. v3（2026-09-16）—— 照抄 BoxDreamer 增强，全线变差

### 3.1 做法

照搬 `refs/BoxDreamer/src/datasets/utils/aug.py` 的三项（参数一一对应）：

```
obj_mask_ratio: [0.0, 0.4]      # 在物体 bbox 内随机挖掉一块
obj_paste_prob: 0.4             # 把别的物体贴上来
rgb_augmethods: ['dark','mobile']
```

实现见 `src/datasets/utils/aug_boxdreamer.py`（用 cv2/numpy 重写，**不依赖
albumentations** —— 它在 py3.11 上要编译 `stringzilla`，装不上）。
两处刻意偏离：遮挡源改成**同帧兄弟实例**（零额外 I/O）；`ISONoise` 强度调到
真实传感器量级、`RandomRain` 压到很低（BoxDreamer 那项是给户外手机的）。

### 3.2 结果：全线变差

| | **v1**（无增强） | **v3**（重增强） |
|---|---|---|
| mean | **4.12** | 22.40 |
| median | **1.44** | 8.35 |
| PCK@0.05 | **96.88%** | 63.81% |
| PCK-AUC | **0.9448** | 0.7030 |
| 失败率>0.1 | **2.22%** | 19.96% |
| 框 IoU | **0.9611** | 0.8505 |

**遮挡分层：**

| `visib_fract` | v1 | **v3** |
|---|---|---|
| 0.0~0.5 | 45.00% | **55.00%** |
| 0.5~0.8 | 27.50% | **50.00%** |
| 0.95~1.0 | **0.79%** | **18.62%** |

### 3.3 ⚠️「差距从 57 倍缩小到 3 倍」是**假象**

`45.0/0.79 = 57×` → `55.0/18.62 = 3.0×`，**差距确实缩小了**。

**但方向是错的**：不是遮挡样本变好（45% → **55%，反而更差**），
而是**完全可见的样本崩了**（0.79% → 18.62%）。**这是欠拟合，不是能力提升。**

### 3.4 原因分析

1. **容量不匹配**：BoxDreamer 用 86M 冻结 DINOv2 + 12 层 transformer、百万级数据；
   我们是 12M ResNet18 + 5k 样本。**同样强度对它只是正则，对我们是学不动。**
2. **更本质：遮挡增强在单图设定下是有害的。** BoxDreamer 输入 **6 帧**，
   查询帧遮掉 40% 别的帧里还看得见，多视图几何能补回来；
   **我们只有那一张裁剪图，遮掉就是纯删信息、没有补偿。**
3. **叠加太多**：`dark` + `mobile` + mask 40% + paste 40% + 原有颜色/模糊/噪声同时上。

### 3.5 改回温和参数（v4，被实例重启打断，未完成）

```
obj_mask_ratio: [0.0, 0.15]
obj_paste_prob: 0.2
rgb_augmethods: ['mobile']        # 去掉 dark（它把亮度压到 0.4 倍太狠）
```

### 3.6 ✅ 从 v3 的失败里提炼出的原则：**「重几何，轻外观」**

v3 失败之后才想清楚，**"让模型不依赖外观"有两种做法，效果完全相反**：

| 做法 | 机制 | 效果 |
|---|---|---|
| **扰动【外观】**（颜色/亮度/模糊/噪声/灰度/随机屏幕纹理） | 让外观**失去判别力** | ✅ **对** —— 模型被迫看形状，**几何完整保留** |
| **遮挡【物体的一部分】**（`obj_mask_ratio` / `paste`） | 把物体盖住一块 | ❌ **错** —— 这是**破坏几何**，不是"轻外观" |

**v3 就是错在第二类**：照抄 BoxDreamer 的 `obj_mask_ratio 0~40%`，
中位误差 1.44 → 8.35 px。**而且它在 BoxDreamer 那里之所以无害，是因为 BoxDreamer 是 6 帧 ——
遮掉的在别的帧里还看得见；我们只有一张裁剪图，遮掉就是纯删信息。**

**准确的表述：**

> **不是「轻外观」，而是「让外观不可依赖」（外观不变性）。几何必须完整保留。**

**为什么这个原则成立**（针对我们的任务）：
8 个角点是**机身 3D 盒**的角点。真实视频里目标多了**亮着的屏幕 / AprilTag 贴纸 / 腕带底座**，
但**这些附件都不改变机身的 3D 盒** —— 所以这是**域差异，不是标签错**，
**外观怎么变都不用重标数据**。

**代码里的缺口**（当时盘点的）：

| 手段 | 有没有 |
|---|---|
| 全局光度增强（颜色/模糊/噪声） | ✅ `augment_image()` |
| BoxDreamer 式 `dark`/`mobile` | ✅ `aug_boxdreamer.py` |
| **语义区域（屏幕）纹理随机化** | ❌ **没有** ← 最对症的一条 |
| **灰度化** | ❌ 没有 |
| **背景屏蔽 `mask_bg`** | ❌ 没有（BoxDreamer 有） |
| **边缘/轮廓辅助监督** | ❌ 没有 |

**→ 据此实现了 `src/datasets/utils/aug_geo_first.py`（GEO1 实验）。**

### 3.7 `aug_geo_first.py` 的两个设计要点

**① 只做外观，明确不做几何**
```
① 白平衡（暖/冷方向的相关偏移）   ② 整体曝光 ±20%
③ 灰度化 p=0.18（废掉颜色）      ④ 亮度/对比度
⑤ gamma                          ⑥ 饱和度偏移（不转色相）
⑦ 高斯/运动模糊 p=0.35            ⑧ ISO 噪声
刻意不做：遮挡、贴别的物体、任何几何变形、任何裁掉物体边界的操作
```

**② 白平衡用「暖/冷相关偏移」，不是「逐通道独立增益」** ⚠️

第一版用的是逐通道独立增益，**预览渲出了洋红/亮绿这种现实中不存在的色偏**。
那不是在模拟相机，**而是在把图弄坏** —— 模型只会学到"这图没法看"，
而不是"颜色不重要，该看形状"。真实相机的白平衡漂移是**色温方向**的：
偏暖 R↑B↓，偏冷 R↓B↑，G 基本不动。

**⇒ 这条修正本身就是 §3.6 原则的应用：「让外观不可依赖」不等于「把图弄坏」。**

```
B1   @ b8d3247 + 弱增强        ->  e4/9/14/19/24 = 30.66 / 24.84 / 21.85 / 19.84 / 18.22
GEO1 @ b8d3247 + 重几何轻外观  ->  同期对比
v1（真实，参照）                ->  30.16 / 26.45 / 22.93 / 20.38 / 19.43
```

**早期轨迹（GEO1 落后，但在预期内）：**

| epoch | GEO1 | B1 | v1 |
|---|---|---|---|
| 4 | **36.99** | 30.66 | 30.16 |
| 9 | **28.55** | 24.84 | 26.45 |
| 14 | **28.15** | 21.85 | 22.93 |
| 19 | **23.57** | 19.84 | 20.38 |
| 24 | **22.58** | 18.22 | 19.43 |
| 94 | 17.65 | — | — |

**强增强本来就会让早期收敛变慢** —— 每张图外观都不同，模型需要更多样本
才能把"形状"这个不变量学出来。**这是 trade-off，不是失败。**
**真正的判据是跑完后的独立评测 + 真实视频表现，不是训练侧的早期数字。**

> ⚠️ 注意：**训练侧指标不能跨代码版本直接比**（v1 训练侧 16.6 ↔ 评测 4.12；
> E5 训练侧 17.18 ↔ 评测 16.75 —— 同样 ~17 的数字，评测差 4 倍）。
> 所以 GEO1 的训练侧数字本身说明不了什么。**这个差异本身也是一条未解的线索。**

## 4. 损失函数消融 —— ⚠️ **在 100 epoch 下不可区分**（结论已修正）

> **本节最初的结论是"损失不是杠杆，三种配置打平"。加了 E4 对照后这个结论被推翻了一半：**
> 见 §4.2b —— **所有这些实验都停在 100 epoch，而 100 epoch 是欠训练。**
> 在欠训练状态下比较损失，测的是"都还没训够"，不是损失的优劣。

### 4.2b 🔴 E4 对照推翻了两个结论

**① 增强不是原因。**
`E4`（**无**增强，100 ep）= **17.23** vs `E0`（轻微增强，100 ep）= **17.91** ——
**统计上无差别**。

**⇒ §3 里"增强有害"的推论是错的。** 轻微增强是**中性**的（既没帮助也没伤害）。
v3 的崩坏来自**重度**增强（`mask 0~40%` + `dark` 把亮度压到 0.4 倍），不是"增强"本身。

**② 真正的杠杆是训练时长。**
`E4`（100 ep）= **17.23** vs `v1`（257 ep）= **4.12** —— **差 4 倍**。
而 E4 和 v1 的配置**完全相同**（同数据、同损失、同无增强），只差训练时长。

**⇒ 100 epoch 远远不够，v1 需要约 257 epoch。**

**③ 由此，E0/E1/E2b/E3b 之间的比较都不可靠。**
它们**全都停在 100 epoch**，即都在学习曲线的陡坡上。
**在欠训练状态下，损失函数的差异被"没训够"完全淹没** ——
E3b（18.31）看着比 E0（17.91）好一点，但这个差距在这个噪声水平下**不构成结论**。

**⇒ §4 原结论「损失不是杠杆」应改成：「在 100 epoch 这个欠训练设置下，损失不可区分」。**
要真正回答损失问题，必须在**充分训练**（≥300 epoch）的条件下重跑。
**E5 就是来验这一点的**（同一份配置 + 300 epoch）。

### 4.2c E0 vs E1 细节（唯一一对同 epoch 的损失对照）

| | E0（fine=2.0） | E1（fine=0） |
|---|---|---|
| mean | **17.91** | 19.58 |
| median | 6.18 | **5.97** |
| PCK@0.05 | 72.93% | **73.34%** |
| PCK-AUC | **0.7616** | 0.7532 |
| 失败率>0.1 | **14.16%** | 15.52% |
| 框 IoU | 0.8788 | **0.8909** |
| 完全可见失败率 | **12.66%** | 14.24% |

去掉占 99.55% 权重的 fine 项后，各项指标在噪声范围内互有胜负 ——
**但注意这一对照同样受 100 epoch 欠训练的限制。**

### 4.3 撤回一个假设

我曾判断"fine 项占 99.5% 把热图监督架空了、训练和推理脱节"。
**实测证伪**：v1 上 `topk` 4.11 px / `soft_argmax` 4.05 px，v2 上 225 / 224 ——
**两种提取高度一致**。脱节的准确表述应该是：

> **没有任何一项损失在优化推理时真正读的那个量 —— "峰在哪、峰有多尖"。**
> coarse 被背景像素（99%）主导；fine 优化的是**质心**，而 `topk` 读的是**峰值格子**。
> 一张弥散的热图质心可以对、峰值却是散的。

### 4.4 ✅ 顺带查出一个真 bug

E2 第一次跑到 **123.6 px** 且不动。根因：

```python
# make_heatmap_target 的 centernet 分支直接用了 gaussian_2d 的输出，**没做峰值归一化**
# 而 focal_loss 的正样本判据是  pos_mask = (gt >= 1.0)
boxdreamer   峰值 1.000000   值>=1.0 的格子数 = 2
centernet    峰值 0.983113   值>=1.0 的格子数 = 0     <- 正样本 0 个！
```

角点中心是浮点数（如 37.3），最近格子到中心的距离不为 0，峰值只有 0.98x
→ **正样本数为 0 → focal 只剩负样本项 → 网络被训成"哪里都没有角点"**。

`boxdreamer` 风格没这个问题（峰值归一化到 1 再映射 ×2−1）；
BoxDreamer 的 `make_bbox_features` 末尾同样做了峰值归一化 —— **我们照抄时漏了这一步**。

**修复后 E2b 从 123.6 → 23.81。** 修复是必要的，只是修好后也没赢过 E0/E1。

## 6. ⚠️ 本轮犯的实验设计错误（**五次**）

**共同毛病：先跑再想，没有先问"这个实验的输出会是什么形状、能不能区分假设"。**
三次都白花了 GPU 时间。

### 错误 1：A/B/C 消融被**种子**混淆

单变量消融"料箱 / 仰角"，三个变体**共用 `seed=424242`**：

| 变体 | mean | PCK@0.05 |
|---|---|---|
| A：无料箱 + 仰角5°（最接近 v1） | 56.16 | 47.9% |
| B：料箱 + 仰角5° | 50.44 | 53.4% |
| C：无料箱 + 仰角22° | 49.49 | 52.1% |

据此得出"料箱和仰角都不是原因"。**但 X1 用完全相同的设置、只换 seed（777001），
结果是好的（mean 6.79 / PCK@0.05 92.5%）。**

**⇒ 那个结论无效，已撤回。** 三个变体共享的那个种子恰好渲出坏场景。

### 错误 2：跨对比时 **epoch 数没对齐**

E0/E1/E2b 全训 **100 epoch**，v1 训 **257 epoch**。
"E0 比 v1 差"**不能**确定是增强的锅，也可能只是没训够。
**这两个变量我从未分开测过** —— 「增强有害」这个说法到现在**还没被证明**。
补测见 §7 的 E4。

### 错误 3：fit 测试**看错了指标**

想验"数据是否自相矛盾"，却：
- 用了 600 个样本（**从零训 200 epoch 本来就不该记住**）
- 设了 `val_ratio=0.1`，读的是 **`val/corner_err_px`（验证集）**

结果 **fit_bin 65~78 px / fit_nobin 44~48 px —— 两个都"失败"，什么也没证明。**

**正确的做法**：极小样本（32 个）+ `val_ratio=0` + 读 **`train/loss_fine`**
（= `SmoothL1(soft_argmax(heatmap), corner_2d)`，像素单位，就是训练集上的角点误差）
+ **必须有 v1 数据的对照组**（若对照组也失败，说明测试本身错了）。

### 错误 4：fit 测试**测的是记忆能力，不是"标签能否从图像推断"**

改对指标后重跑：`fitc_v1` **1.481 px** ✅ / `fitc_bin` **2.262 px** ✅
（32 样本，800 epoch，读 `train/loss_fine`）

**两个数据集都能被拟合。** 于是得出"料箱数据自相矛盾"的结论**不成立**。

**根因**：**记忆不需要标签能从图像推出来。** 一个 12M 参数的模型完全可以把 32 组
（图像, 坐标）硬背下来 —— **哪怕坐标是随机的**。

**⇒ "能不能拟合"回答不了"标签能不能从图像推断"。这个问题用拟合测不出来。**

**修正后的表述**：
- 「存在裁剪图是空白平面、却配 8 个具体角点的样本」—— ✅ **成立**，那是**直接观察**（§2.6 的 5 样本图），不是统计推断
- 「这些样本是 v2 训练不收敛的原因」—— ❌ **未证明**。要证明需要做**剔除实验**：从 v2 里去掉 `visib_fract < 0.3` 的样本重训，看验证集是否改善

### 错误 5 ⚠️ **整组损失消融都在测"欠训练"**（最贵的一个）

E0/E1/E2b/E3b **全都停在 100 epoch**，而 E4 的对照显示 **100 epoch 是欠训练**
（17.23 vs v1 在 257 epoch 的 4.12）。

**⇒ 在欠训练状态下比较损失，测的是"都还没训够"，不是损失的优劣。**
四次 100-epoch 训练（约 4.5 GPU 小时）**不具备区分能力**。

**解法**：比较损失必须在**充分训练**（≥300 epoch，或被验证过已达平台期）的条件下做。
**更好的做法是先跑一条"训练时长 vs 指标"的曲线**，确认进入平台期后再做消融 ——
否则消融的任何差异都可能只是"谁在陡坡上跑得快一点"。

- **影响文件**：`docs/RESULTS.md` §4
- **共同教训**：
  - ⚠️ **做消融之前，先确认"被测变量的差异 > 其它未控变量的影响"。**
    epoch 数、随机种子、数据划分都是"未控变量"，它们在实验设计里必须被**显式固定或扫掉**。
  - ⚠️ **"两个配置看起来差不多"之前，先问"它们是不是都被同一个瓶颈卡住了"。**
    都卡住的时候，比较是无效的。
  - ⚠️ **一个 30 秒的预实验（跑 5 epoch 看 loss 曲线的斜率）能避免几小时的无效训练。**

### 7.1 证据链（`val/corner_err_px`，epoch 4 / 9 / 14 / 19 / 24）

| `B1` | `b8d3247` | 30.66 | 24.84 | **21.85** | 19.84 | 18.22 | ✅ 好 |
| `B2` | **`c21194c`** | 44.13 | 40.33 | **35.09** | 34.43 | 30.47 | ❌ **回归点** |

**重做要求**：一次只跑一个；记录每 epoch 墙钟时间并与独占时核对。

### 7.3 已经排除的（关于回归的具体位置）

`c21194c` 只改了 4 个文件。`datamodule.augment = False` 已用 Hydra 组合确认**确实生效**，
所以该提交在 `augment=false` 时活跃的改动理论上只有：

1. `__getitem__` 多了两个返回键（`visib_fract` / `px_count_visib`）→ **P1 已排除**
2. 新增的 `__init__` 参数 + `self._rng` 创建 → 理论无害
3. 新增的模块导入 → 理论无害
4. 新增的 5 个方法（`_bbox_in_crop` / `_pick_foreign_object` / `_paste_foreign` …）
   全部只在 `if self.augment:` 内被调用 → 理论无害

**⇒ 理论上都不该有影响，但实测有。所以我的"代码阅读"在这一处是错的 —— 必须靠重做的干净对照来定位，不能再靠读代码推断。**

### 7.4 结论：**不是数据问题**

**同一份数据、同一个损失、同一个 seed，只有代码版本不同：**
`24d511b` / `b8d3247` 好（22.9 / 21.9），`c21194c` 及之后坏（35.1 / 27.5）。

**⇒ 数据是好的。** 旁证：
- 用 v1 的 checkpoint 评这份数据 → median 1.44 px（`probe_v1`，在实例上用同一份脚本复现）
- 数据自洽性检查全过（标签、几何、dataloader、掩码对齐）
- `fitc_v1` = 1.481 px / `fitc_bin` = 2.262 px，都能拟合

### 7.5 最贵的一条教训

> **扫变量之前，先用当前代码复现基线。没有复现的基线，所有对比都是无效的。**

我在扫"数据 / 增强 / 损失 / epoch / 主干"这五个变量时，**一次都没有先做这件事**。
代价：**四天 GPU 时间 + 一批不可用的结论**。
而这一条检查的成本只有 **40 分钟**（25 epoch 对照，看 `epoch14` 的 `corner_err_px` 是否 ≈ 22）。

**⇒ 已经需要一个"回归检查"脚本**：任何改动后跑 25 epoch，`epoch14` 偏离基线超过 10% 就报警。

| **v1** | v1 | 无 | smooth_l1+fine2.0 | 257 | **16.6** | **4.12** | **96.88%** |
| E4 | v1 | 无 | **完全相同** | 100 | 18.15 | 17.23 | 71.42% |
| **E5** | v1 | 无 | **完全相同** | **300** | **17.18** | **16.75** | 78.07% |

**两个矛盾：**
1. **300 epoch 只比 100 epoch 好 0.5 px** ⇒ **训练时长不是原因**（推翻了 §4.2b 的结论）
2. **v1 的训练侧 16.6 与 E5 的 17.18 几乎一样，但独立评测差 4 倍**（4.12 vs 16.75）

**⇒ 存在一个尚未找到的第三个变量。** 两种可能：
- (a) **评测口径有隐藏差异**（两次评测不是同一份脚本/划分/数据）
- (b) **v1 那个 checkpoint 和我以为的不是一回事**（例如被后续运行覆盖过）

**判别实验（probe）**：把**本地**的 v1 checkpoint（本地评它得 4.12）传到实例，
用**和 E4/E5 完全相同的命令**评它。
- probe ≈ 4.12 ⇒ 评测一致，**E 系列的模型真的更差**，差异在训练
- probe ≈ 17 ⇒ **本地那个 checkpoint 不是我以为的东西**

> ⚠️ 第一次上传被截断了（实例上只有 104 MB / 本地 141 MB），必须校验文件大小再评测 ——
> 这也是一个教训：**跨机传大文件后要校验完整性**，不能只看"命令返回了"。

## 9. 对任务本身的认识（回答"看不见的样本该怎么标"）

**要不要预测被遮挡的角点？要。** 因为任务是 6D 位姿估计，位姿需要**完整盒子**。
amodal 标注是标准做法，**"外推被挡住的角点"正是这个任务的价值所在**。

**但"要不要预测"和"能不能拿来训练"是两件事。**

> **一个训练样本必须是一个「有确定答案的问题」。**

| `visib_fract` | 图像里的证据 | 能否训练 |
|---|---|---|
| **< ~0.1** | 几乎为零 | ❌ **纯噪声，而且有害**（教模型学伪相关） |
| 0.1 ~ 0.3 | 很薄，位姿可能欠定 | ⚠️ 边缘 |
| **0.3 ~ 0.8** | 可见部分足以定住位姿 | ✅ **正是我们要的** |
| > 0.8 | 充足 | ✅ 普通样本 |

**光看 `visib_fract` 不够，还有三条硬要求：**

| # | 要求 | 违反的后果 |
|---|---|---|
| 1 | 可见证据要够（`visib_fract` **和** `px_count_visib` 都设下限） | 标签无从推断 |
| 2 | **物体不能被画面边界裁掉** | 角点落在图像外，像素坐标**无定义** |
| 3 | **裁剪框必须框住目标**（用 `bbox_obj`） | 裁剪取到别的区域 |
| 4 | **裁剪图里目标必须可辨识** | 一箱同款物体、标签指向其中一个 → 答案歧义 |

**注意 1 和 2 是不同的问题**：**遮挡**（被别的物体挡住）位姿仍可外推 ✅；
**截断**（被画面边界切掉）角点在图像外的坐标**根本不存在** ❌。

**我们当前只查了 1 的一半**，完全没查 2、3、4。

**设计上应该怎么做（针对"只有一个物体类别"这个特点）：**
1. `visib_fract` 下限 0.10 → **0.25~0.3**
2. 裁剪**以 `bbox_obj` 为中心**（目标永远在裁剪图中心、尺度已知）
3. 排除 `bbox_obj` 部分出画的实例
4. **遮挡的"度"要可控** —— 料箱随机堆叠太不可控（18% 全挡死）。
   **更可控的是"训练时合成遮挡"**：拿完全可见的样本在线遮掉一块，
   **每一张的答案都唯一确定，遮挡比例由你定。**
   （注意 §3：强度必须小 —— 遮 10~15% 恰好，遮 40% 就把证据删光了。
   遮挡增强的目的**不是让图像变难，而是在答案仍唯一的前提下教模型外推**。）

## 11. GEO2~GEO6：把「加遮挡」这件事从头做对（2026-09-19）

### 11.1 背景

### 11.2 GEO2：第一次尝试，全线崩溃

配置：料箱 0.16 m + 12 相机 + 6 干扰物（**全部参与物理**）

```

训练      300 epoch 跑完，但 corner_err_px 从 99.7 只降到 82.7（几乎没学）

          bbox_visib 宽中位 104 px（v1 是 122）
```

**画面里大片黑帧、物体在半空翻滚**（`data/results/geo2_render/s24.png`）。

**⇒ 一半的监督信号是垃圾，模型学不动。**

### 11.3 三层根因（逐个试过，前两个是错的）

| # | 我猜的原因 | 结果 |
|---|---|---|
| ① | 料箱逼出 `randombin` 分支（注释明写「不做相交检查」） | 默认去掉料箱 → **没用** |
| ② | 干扰物只沿 z 叠、xy 重合 → 互相穿透 | 改黄金角螺旋 → **位置一模一样，没用** |
| ③ | 薄片物体的 CONVEX 碰撞体退化 → 穿地板 | 改 BOX → **位置一模一样，没用** |

**⇒ 最小复现（单个干扰物 + 地板）直接推翻了 ①②：**
```
导入后世界最长边 99496.9 mm -> 归一化 want=51.8 实际=51.8  ✓
物理后 loc=(0.147, -0.021, 0.006) —— 稳稳落地 ✓
```
**干扰物单独掉是好的，只有「和 6 个相机 + 地板一起模拟」时才炸。**

**修法：干扰物改成【静态摆放】（`enable_rigidbody(False)`）—— 没有刚体就没有爆炸。**

### 11.4 新增的「位置校验门」——这次事故的解药

在物理塌落**之后**、写盘**之前**加一道门：

```python
for o in 所有物体:
    if not (-0.6 < x < 0.6 and -0.6 < y < 0.6 and -0.1 < z < 0.6):
        raise SystemExit("scene broken -- aborting instead of writing garbage")
```

**它 30 秒就抓到了 GEO3 的爆炸**（`prop_01 @ z = -18.76 m`），
而不是烧掉 8.5 小时渲染 + 4 小时训练才发现。

**⚠️ 而我在 v2 失败时就写过 `scripts/qa_scene.py` 当质检门，却没接到流程里。**
**「知道该做什么检查、工具也写了，然后在流程里漏掉」是这一轮最贵的错误。**

### 11.5 GEO3：场景健康，但**没有遮挡**

去掉料箱后渲染干净了（3 场景全部通过校验），但分布和 v1 几乎一样：

```
       实例数   中位visib  >=0.1可用   部分遮挡(0.1~0.95)
v1      5000     1.000      99.4%          3.4%
GEO3      48     1.000     100.0%          4.2%
```

**原因：`sample_poses()` 强制物体互不相交。**

### 11.6 四组「造遮挡」尝试——全部失败，而且暴露了一个硬矛盾

```
配置                    实例数  中位visib  >=0.1   部分遮挡  严重<0.3
tight (spawn_half .06)    72    1.000    100.0%     0.0%     0.0%   ← 收紧反而更不重叠！
mid   (spawn_half .09)    72    1.000    100.0%     4.2%     0.0%
stack (步距 .060)         24    1.000    100.0%     0.0%     0.0%
stack (步距 .075)         72    1.000     95.8%     1.4%     4.2%
```

**⇒ 硬矛盾：`sample_poses()` 的相交检查是「防爆炸」和「造遮挡」之间的零和。**
- 有相交检查 → 物体永不重叠 → 遮挡恒为 0
- 没相交检查 → 深度穿透 → 物理爆炸（GEO2）

### 11.7 ✅ GEO6：用「静态压盖」两全其美

**关键洞察：干扰物是静态的，静态物体重叠【不产生任何力】—— 所以既能遮挡又绝不会爆炸。**

给 `add_objaverse_props` 加 `target_objs` / `cover_ratio`：
随机挑一个目标，把干扰物静态摆在它上方偏一点；`cover_ratio` 控制水平偏移
（0 = 完全对中遮最狠，1 = 完全错开不遮）。

```
配置              实例数  中位visib  可用    部分遮挡  完全<0.1  严重<0.3
v1（对照）         5000    1.000     99.4%     3.4%     0.6%     1.1%
cover 0.0            24    1.000    100.0%     4.2%     0.0%     0.0%
cover 0.5            72    1.000     97.2%     8.3%     2.8%     6.9%   ← ✅ 采用
```

**`cover_ratio=0.5`：严重遮挡 6.9%（v1 的 6.3 倍），而可用率仍有 97.2%。**

**完全遮挡的被数据加载器正确剔除：**
```
cover c05 -> 丢掉 1 个 px_count_visib<64、1 个 visib_fract<0.1，保留 70 个样本
```

## 13. 两个关键发现：预测角点不成盒子 / 合成集与真实视频排名反转

### 13.1 ⚠️ 预测出的 8 个角点**不构成长方体投影**

**现象**：把预测的 8 个角点连成 BB8 线框，形状是乱的 —— 面自交、四条深度棱指向
不同方向。

**判据**（合法长方体投影的三个必要条件）：
1. 两个面（BB8 的 0-3 / 4-7）各自是**简单四边形**（不自交）
2. 四条深度棱 (0-4, 1-5, 2-6, 3-7) **近似平行**（同一消失点，夹角应 < 10°）
3. 深度棱长度比接近 1

**实测（目标视频 frame 0）**：

| 模型 | 面自交 | 深度棱最大夹角 | 深度棱长度比 | 合法？ |
|---|---|---|---|---|
| train_v1 box0 | 面1 ❌ | **78.0°** | 5.08 | 否 |
| train_v1 box1 | 面0/1 ❌ | 82.1° | 2.56 | 否 |
| GEO1 box0 | 无 | 72.1° | 1.65 | 否 |
| GEO1 box1 | 面0 ❌ | 87.8° | 3.69 | 否 |
| GEO7 box0 | 面0 ❌ | 89.9° | 10.39 | 否 |
| GEO7 box1 | 无 | 85.1° | 5.91 | 否 |
| （手工构造的合法投影） | 无 | **0.0°** | 1.00 | **是** |

**⇒ 6 个预测全部不是长方体。**

**根因：架构决定的。** `src/models/utils/prediction_utils.py`：

```python
def argmax_2d(heatmap):
    B, K, H, W = heatmap.shape
    idx = heatmap.reshape(B, K, -1).argmax(dim=-1)   # 每个通道【各自】取最大值
```

模型输出 **8 张热图**，每个角点**独立**取最大值 ——
**第 3 个角点算错，不会影响第 5 个角点**。

损失函数也是逐角点的：
```
loss = Σ_i ‖预测角点_i − GT角点_i‖
```
**没有一项在问"这 8 个点合起来像不像一个盒子"。**

**后果**：我们训练的是**「8 点检测器」**，不是**「位姿估计器」**。
在训练分布内它靠记忆能蒙对；一旦某个角点被遮挡或外观陌生，
它只能凭"记忆里的平均位置"猜，**没有任何机制把它拉回到其余 7 点所暗示的盒子上**。

**修复方案**：

| 方案 | 做法 | 评价 |
|---|---|---|
| A. PnP 后处理 | 用预测的 8 点跑 PnP 求位姿，再**重新投影**出 8 点 | 代码里 `recover_pose_from_bb8` 已有；但不消除原始误差 |
| **B. 位姿参数化** | 网络直接预测 6D 位姿，角点是**推导**出来的 | **根治** —— 结构上不可能输出非法盒子 |
| C. 几何一致性损失 | 逐角点 loss + 惩罚项 | 软约束，不保证 |

**⚠️ 与题目要求的冲突（待与 psd 确认）**：
psd 确认「交付物是 2D 的 8 个角点，不需要相机内参」。
- 方案 A 需要内参 K 才能跑 PnP
- 方案 B 若不预测内参，就退化成 A

**⇒ 需要问清楚：题目要的是「8 个角点的像素坐标」，还是「可解释为长方体的 8 个角点」？**

### 13.2 🎯 合成测试集与真实视频的**排名完全反转**

| | 合成测试集（248 样本 / 1984 角点） | **目标视频 frame 0**（2 个手工框） |
|---|---|---|
| **v1** | mean **4.12** px / PCK@0.05 **96.88%** | IoU 0.435 / 0.539 → **0.487** |
| **GEO1** | mean 16.37 px / PCK@0.05 79.28% | IoU 0.697 / 0.516 → 0.606 |
| **GEO7** | mean **39.21** px / PCK@0.05 **48.64%** | IoU **0.897 / 0.731 → 0.814** |

**⇒ 合成集上最烂的 GEO7（差 9.5 倍），在真实视频上最好（IoU 高 0.33）。**

**为什么**：
- v1 的合成测试集和 v1 的训练集**共享同一套外观统计**（同批纹理、同一屏幕、同种光照）
  -> v1 "过拟合到外观"，合成集分数虚高
- GEO7 用 **1923 个随机资产 + 随机屏幕内容 + 随机色温/曝光**，
  逼模型学**几何**而非**外观** -> 合成集分数暴跌，但换到真实视频反而更准

**⇒ 这是「重几何、轻外观」的实证，第一次有了量化对比。**

**⚠️ 证据强度不足**：视频上只有 **2 个框 / 1 帧**。
这个结论目前只能算**强信号**，不能当定论 —— 需要抽 8~10 帧补标注验证。

## 14. 多实例架构：让模型同时预测多个 DJI（2026-09-21）

### 14.1 动机

目标视频里经常出现**多个同类相机**。原来的单实例裁剪只监督一个物体，
模型只能靠"目标在裁剪图中心"这个位置先验去猜 ——
实测 **88.3% 的裁剪图里混进了其他实例**。

**改成多实例后，"哪个是目标"这个问题就不存在了：框内所有实例都是目标。**

### 14.2 设计（零内参、不需要检测器、不需要 SAM）

```
输入:  裁到 2.5x 物体框（自然装进 2~8 个实例）
输出:  ① 1 通道【物体中心热图】   峰的个数 = 实例个数
       ② 16 通道【角点偏移】      在每个峰的位置读出 8 个角点
解码:  中心热图 NMS -> N 个峰 -> N x 8 角点
```

| 组件 | 实现 | 说明 |
|---|---|---|
| 数据集 | `BOPPBRDataset(multi_instance=True)` | 裁剪放大到 2.5×，**框内所有实例都监督** |
| 模型 | `HeatmapDecoder(center_heatmap=True)` | 主头 8 → 1 通道；**骨干 11.2M 不变**（总 12.2M） |
| 损失 | `multi_instance_loss` | 中心 focal + 角点回归 + **几何一致性** |
| 解码 | `decode_instances` | max-pool NMS + 按距离贪心 NMS |
| 评测 | `MultiInstanceLightningModel._eval_instances` | recall / precision / err_matched / geo_resid **四项分开** |

**关键：数据不用重渲。** `crop_and_resize` 会返回调整后的 K，
用它投影 `scene_gt.json` 里**所有**实例的位姿就直接得到裁剪坐标系的角点。

### 14.3 数据集标签普查（本轮的副产品）

| 数据集 | 帧 | 标签实例 | 每帧 | 可见性中位 | 完全遮挡<0.1 | 严重遮挡<0.5 |
|---|---|---|---|---|---|---|
| v1 | 500 | 5000 | 10 | 1.000 | 0.6% | 1.6% |
| **GEO7** | 700 | **4200** | 6 | 1.000 | **5.8%** | **9.0%** |
| GEO2（废弃） | 500 | 6000 | 12 | **0.204** | **48.6%** | 53.1% |

**⇒ GEO7 的严重遮挡是 v1 的 5.6 倍，完全遮挡是 9.7 倍。**
（v1 每帧 10 个实例，但多实例裁剪里平均只装进 4.6 个 —— 其余在画面外。）

### 14.4 ⚠️ 定位并修复的四个 bug

**① 缺 `val/corner_err_px`** —— `ModelCheckpoint` 监控这个键，
多实例模块没记 → 第 4 epoch 触发保存时抛异常退出。
**表现是"训练卡住"（其实崩了），白等 54 分钟。**
修：补记该键（多实例下 = `err_matched`）；`nan` 会静默不记录，用哨兵值兜底。

**② 🔴 GT 中心热图的峰不在整数格点上 → focal 零正样本**
数据集把高斯峰放在浮点位置 `gx = center_x * scale`，
**没有任何格点的值恰好是 1.0**；而 focal 用 `pos = (gt >= 1-1e-4)` 判正样本
→ **一个都匹配不到 → 中心头完全没有正监督 → 塌缩成"处处无物体"**。

```
实测: 8 个实例的 batch，GT 正样本格数 = 1
      中心热图预测值处处 ~0（全图最大值中位 0.0017）
      recall = 0.000
```

**这解释了为什么"角点学得很好（27.7 -> 4.7）但中心头不学"**
—— 角点损失直接在 GT 中心格子上算，不依赖热图峰。

**⚠️ 这是 `ALGO-08`（focal 零正样本）的同一个坑，第二次踩。**
修（三处，互为保险）：
1. 数据集：高斯峰对齐到整数格点 + 显式置 1.0（CenterNet 的标准做法）
2. 损失：正样本判据 `1-1e-4` → `0.9`
3. 损失：正样本数为 0 时**大声警告**，不再静默
4. 加回归测试 `test_gt_heatmap_has_exact_peaks`

**修后**：全图最大值中位 0.0017 → **0.8186**；GT 中心处 >=0.3 的比例 0% → **81.2%**

**③ eval 的设备不一致**
`decode_instances` 返回 CPU numpy，而 `gt_centers` 在 GPU → 匹配循环报
`Expected all tensors on the same device`。

**⚠️ 这个 bug 之前被 ② 掩盖了：`n_pred=0` 时匹配循环体根本不执行，
所以不报错。修好 ② 之后 `n_pred>0`，它立刻暴露。**
**⇒ 修好一个 bug 会暴露下一个 —— 这是调试的正常现象。**

**④ 🔴 `decode` 的 `center` 坐标系与 `corners` 不一致**
```python
"center":  (xs, ys)              # 热图格坐标 0~64
"corners": corners * stride      # 裁剪像素  0~256    ← 差 4 倍
```
匹配时拿 `center` 和 `inst_centers`（裁剪像素）比 → 距离 50~150 px
→ 超过 `match_dist=20` → **全部匹配失败**。

**这个 bug 极其隐蔽**：解码出的**数量**和 GT 完全一致（每批 4.1 vs 4.1），
只看 recall 会误判成"检测器没学会"。

**⇒ 只有逐级追踪才能定位：**
```
GT 实例数                      132
max-pool NMS 后 >= 0.3 的格点  每批 4.1
解码出                         每批 4.1     <- 数量对
匹配上                         6 / 132      <- 位置全错
```

修后：**recall 0.0455 → 0.9318** ✅

### 14.5 用户的怀疑：几何约束是不是搞坏了模型？

**做了 `geo_weight=0` vs `=1` 的对照实验**（其余完全相同，并行跑 30 epoch）：

```
                有 geo    无 geo    差异
tr_loss (e29)    4.89      5.04      3%
center           0.461     0.490     6%
corner           4.418     4.546     3%
recall           0.032     0.032     0%
```

**⇒ 逐项几乎逐位相同。几何约束不是元凶，反而略好。**
**⇒ 但同时也说明：`geo_weight=1.0` 太小了，几何项只占总损失的 0.16%（4.418 vs 0.0077），
现在是个摆设。要让它起作用，权重要按【梯度量级】匹配调到 10²~10³，不能盲调。**

### 14.6 本轮方法论教训

1. **`missing=0` 这个检查每次都要看。** 我用"手搓 config"做诊断，
   结果 `missing=221 unexpected=260` —— **模型根本没加载，跑的是随机权重**，
   差点据此得出错误结论。今天在这上面栽了两次。
   正确做法：诊断脚本必须走 `@hydra.main`，和训练用同一套配置。
2. **逐级追踪 > 看聚合指标。** bug ④ 的表现是 "recall=3%"，
   如果只看这个数字会去调 NMS 和阈值；逐级追踪（GT 数 → NMS 后格点 → topk
   → 匹配数）一次就指出"数量对、位置错"。
3. **数量对得上不等于结果对。** bug ④ 里解码数量和 GT 数量完全一致，
   唯一的问题是坐标系差 4 倍。
4. **一次只改一个变量。** 多实例训练刻意用 **v1 的数据**（而不是 GEO7 的），
   因为 GEO7 数据集本身有未定位的问题；同时换架构和数据会导致无法归因。
